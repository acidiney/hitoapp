# Implementation status

The full release scope is in [release-plan.md](release-plan.md). This repository is a development build. The public release is not ready.

## Current quality work

The structural refactor, first substantial UI composition pass, tag-independent recording identity, multiple-folder Settings, artist/album pages, personal recording and album title/artist fields with source provenance, and personal HTTP plugin installation are implemented. Rust uses cohesive capability services with private SQLite storage, opaque authenticated actors, explicit backend device ownership, small HTTP adapters, and generated contracts. React uses focused pages and workflow hooks, a recording spotlight and artwork grid/list, grouped navigation, a listening sidebar, expanded player, and tabbed settings. Development setup launchers generate read-only Docker mounts from native folder selections. See [architecture decisions](architecture-decisions.md), [interface direction](../DESIGN.md), [folder behavior](music-folders.md), and the actual [TODO checklist](../TODO.md).

Provider search and adoption now have authenticated application APIs, live connection authority, and durable owner-only recordings with provider provenance. The existing audio API can relay provider bytes through a separate bounded media client. The discovery UI now searches, pages, saves, and plays through those APIs. The normal server is healthy on migration 0020 after a stopped-volume backup and read-only preservation audit. Playback-time source refresh/recovery remains unfinished. See [the content protocol and boundaries](plugins.md#provider-content-groundwork).

## Provider audio and application APIs

`Catalog::open_audio` owns authorized local/provider streaming. The HTTP adapter maps its typed metadata and pull stream into GET/HEAD responses. Provider HTTP types, approved endpoints, saved credentials, admission, and ongoing database authority stay private to core. Search/adoption routes use the existing authenticated extractor and core capability operations; Rust routes generate their OpenAPI and TypeScript.

Eighteen targeted core/HTTP/logging tests pass in `/tmp/hito-provider-audio-review-green.log`. They cover original WAV bytes, opaque source query encoding, single ranges, HEAD/If-Range, header and credential isolation, malformed/redirected/framing responses, premature EOF, at-most-64-KiB yields, active read stalls, healthy long reads and consumer pauses, ten held streams across five accounts, cancellation/drop cleanup, pending removal, unread bodies after cross-instance credential clearing, service withdrawal, and harmless readiness/check changes. The application search/adopt/audio workflow also passes its private two-account HTTP test.

Two independent review cycles found and resolved two defects. Reqwest's body read timer incorrectly counted consumer pauses; the deadline now wraps only an actively awaited read. Unsupported transfer coding and Transfer-Encoding plus Content-Length were accepted; raw HTTP fixtures now prove rejection before body publication. All three final security/correctness/performance verdicts pass. Mandatory Clippy also led to boxing the large content result rather than suppressing its warning.

The performance reviewer populated 100,000 provider recordings across ten accounts through Docker Python SQLite. Opening and ongoing authorization use indexed source/installation/service/recording and membership lookups. After ANALYZE, they took 57 and 91 VM steps in that diagnostic. This establishes query shape, not SQLx request latency, sustained browser backpressure, global-limit saturation, or release performance.
