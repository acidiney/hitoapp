# Packaged provider outage and upgrade gate

This opt-in Chromium gate uses a real packaged server, shared React UI and an owned HTTP plugin. It does not build, pull or install anything. It never addresses the normal Hito server or a VPS.

The browser creates an administrator, disables external metadata enrichment, selects two synthetic music folders, approves a plugin and imports three playlists through the UI of a frozen version 54 runtime. Typed public commands create private metadata, likes, saved progress, a manual source choice and three automatic-resolution receipts covering ready and empty results. Originals and duplicate playlist occurrences remain separate objects.

The browser leaves the application while its wrapper stops the old server and runs the new packaged executable's `migrate --database /data/outage.db --expect-version 54` command. Its real receipt must report previous version 54, current version 55 and exactly one applied migration. A namespace keeper keeps a uniquely owned memory-backed data volume mounted throughout this transition. The new runtime opens that database, serves its own bundled assets, and must retain the exact public snapshot and all three old command receipts. Each original command UUID is replayed after the migration and must return its identical receipt without provider work.

The real plugin then returns `503` from its source endpoint. The first resolution reaches the backend, and only its HTTP acknowledgement is discarded. The automatic retry must send identical bytes and UUID, return the same real receipt and repeat no provider work. This is one accepted operation with two intentional wire attempts. The UI must describe a service outage. Selecting Play again after provider recovery must create a new UUID, decode the owned PCM16 WAV, report its 90 second duration and continue advancing across Inertia navigation.

A separate queue contains healthy audio, an unavailable entry and another occurrence of the healthy recording. Lookahead must leave current audio untouched. The browser uses the actual seek control near the end and observes a real media `ended` event and queue continuation. It never synthesizes an application response or media event. Private untouched playlists, duplicate identifiers, metadata, likes, progress, source choices and original file hashes remain unchanged. Only actually heard recordings may gain progress. No Download control is selected, download writes remain zero, and recording and playlist download-status replies remain canonically absent.

## Inputs and command

Provide exact image IDs, source commits, product fingerprints and clean source checkouts for both runtimes:

- `HITO_PACKAGED_IMAGE`, `HITO_PACKAGED_SOURCE`, `HITO_PACKAGED_INPUTS`, `HITO_PACKAGED_WORKTREE` identify the new runtime containing migration 55 and the typed outage outcome.
- `HITO_OUTAGE_LEGACY_IMAGE`, `HITO_OUTAGE_LEGACY_SOURCE`, `HITO_OUTAGE_LEGACY_INPUTS`, `HITO_OUTAGE_LEGACY_WORKTREE` identify the frozen version 54 runtime.
- `HITO_OUTAGE_BROWSER_IMAGE` identifies the existing Playwright 1.56.1 Noble image.
- `HITO_OUTAGE_NODE_IMAGE` identifies the existing Node 22 image.
- `HITO_OUTAGE_MODULES_VOLUME` names an already-existing, qualified local Compose `node-modules` volume. The runner validates its identity and mounts it read-only for the module-pin check.

With these inputs, run `python3 scripts/provider-outage/run-packaged.py` from the gate checkout. The selected external modules volume mounts read-only. Empty ignored mount directories may be created in the source checkout; application files remain read-only. Product image labels and source fingerprints are checked before starting services. The existing read-only module-pin helper verifies the exact version and content of @playwright/test, playwright and playwright-core before and after execution. Their receipts must match.

There are no published ports or Docker socket mounts. The namespace keeper has no network, and the browser, real provider and active application share only its loopback namespace. Old and new servers run sequentially. The keeper holds fresh 96 MiB data and 1 MiB private-control tmpfs volumes; both are removed by exact ownership at cleanup. The browser has a 1 GiB memory limit, 256 MiB shared memory and 272 MiB temporary filesystems. The active server has a 512 MiB memory limit and 16 MiB temporary filesystem. The keeper has 64 MiB, and fixture preparation and migration each have 512 MiB limits and run separately.

Screenshots, traces and video are disabled. Docker retains bounded rotating json-file operational fixture logs. Console captures and extracted runtime logs are checked in bounded process memory against synthetic private canaries. The temporary private registry stays in the owned control tmpfs and is read through a bounded pipe. Raw logs, credentials, provider identifiers, titles and URLs are never written to the evidence directory. Reports contain fixed counters, hashes, outcomes and timings. Every Docker command has an output bound and deadline. Cleanup checks exact invocation labels and immutable container identifiers before removal. Confirmed absence during discovery is harmless. A failed identity check or removal does not stop independently verified cleanup, and failures are aggregated. Only owned tmpfs volumes are removed, and a nonzero incoming result is preserved.
