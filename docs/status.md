Account deletion is implemented and runs on the local development server (migration 0067). An administrator deletes another account from Settings > Accounts by typing its name (`DELETE /api/v1/users/{id}`, the generated contract carries `DeleteAccount`); `Identity::delete_account` refuses non-administrators (403), unknown accounts (404), the administrator's own account, a mistyped or stale name and the last administrator (409). One transaction revokes every session and erases the account's corrections, downloads and their receipts, playlists, likes, history, progress, personal edits, podcast subscriptions and receipts, provider installations with their encrypted credentials, reporter credentials, artwork, jobs and personal provider library; managed download files are listed in a ledger in the same transaction and removed by the download worker afterwards, including after a restart. Foreign keys are deferred to commit, so a table the plan misses makes the deletion fail and roll back, and a schema-driven unit test fails when a new table that can reach `users` is not part of the plan. ## Source-specific speed negotiation and conversion

Current behavior: `hito-audio` converts sources at 352.8, 384, 705.6 and 768 kHz (integer decimation by two or four with a Kaiser FIR, giving 176.4 or 192 kHz) and sources with more than two channels (ITU-R BS.775 style downmix, front channels at unity, centre and surrounds at -3 dB, low-frequency channels dropped, followed by a peak limiter that holds output at or below full scale) before time-stretching, at every speed; other sources are forwarded unchanged. Other rates above 192 kHz are rejected by the decoder with a typed unsupported error because they would decimate to rates devices do not open. Before the converter is built the worker negotiates the output representation with the default device (a supported rate is kept; otherwise a same-family rate, the device default or the nearest offered rate is chosen) and the converter decimates by an integer factor or resamples with a polyphase windowed-sinc stage to it; mono is duplicated for stereo-only devices. See [output negotiation](native-audio.md#output-negotiation). This was added after the built-in MacBook speakers, which do not offer 176.4 or 192 kHz, failed to open 384 and 352.8 kHz files with an output-unavailable error. Layouts without speaker positions use the default speaker order for 3 to 8 channels. Converted positions follow packet times and never pass the source duration. Each opened source reports a speed capability from its decoded sample rate and channel count. The native owner derives `effective_speed` from the chosen speed and the source's reported `speed_support`, so it never lags a speed command; a source that cannot present the chosen speed plays at 1.0 without failing and the chosen speed returns with the next capable source. The browser player verifies the rate the media element accepted and returns the element and its default rate to 1.0 after a refusal. The shared speed menu and a non-blocking notice use these fields. See [conversion and speed capability](native-audio.md#conversion-and-speed-capability).

Tested evidence (Linux Docker, clocked PulseAudio monitor): 15 default conversion tests plus 4 converter unit tests (capability table including non-family rates, output formats, bit-exact forwarding, tone/duration at 384, 705.6 and 768 kHz, out-of-band rejection, rejection of 200, 220.5 and 250 kHz, 5.1 per-channel weights, front-only level equal to stereo, limiter bound and recovery on a loud 7.1 mix, default layouts for 3 to 8 unpositioned channels, packet-time re-anchoring, duration clamp, seek, cancellation); 9 tempo monitor cases including converted 384 kHz, 352.8 kHz and 5.1 sources at 1.0, 2.0 and 0.5 with pitch and duration measured, mid-playback speed changes, seek and cleanup; one playback-owner monitor case for a 384 kHz source (range 500-3000, effective speed 500 then 2000, with every observed snapshot across the speed command showing effective equal to chosen); two owner unit tests that feed engine updates after a speed command and cover the unit-only fallback and restoration on the next capable source; DOM tests and browser-player tests for range, notice, restoration, refused/throwing rates, default-rate reset and continuation speed.

Output negotiation and resampling evidence (Linux Docker): 7 pure selection tests, 6 converter tests (frame counts, tone level and frequency, alias rejection, seek and flush, bit-exact forwarding, mono duplication, surround plus rate change) and 2 monitor cases where a device restricted to 48 kHz plays 384, 352.8, 192, 176.4 and 44.1 kHz sources at 1.0, 0.5 and 2.0 with the converted rate reported by `Player::output_format`, pitch checked, and a device with no usable rate failing with `OutputFormat`. The monitor restriction is a test hook that filters the rates the real virtual device offers; it does not exercise CoreAudio. `reversing_a_pending_rate_change_does_not_end_the_stream_early` and `sources_above_the_device_limits_play_at_unit_speed_in_converted_form` time out intermittently on the shared monitor (the first also fails on the commit before this change, two of five runs); the cause is not yet diagnosed.

Limits: no decoder-accepted native source reports unit-only, so native fallback is verified by owner unit, DOM and mock-media tests rather than a device fixture. 705.6 and 768 kHz sources are covered by conversion tests, not by a monitor fixture. Sources above 192 kHz are no longer bit-exact at 1.0. The failure for a device that cannot play a file is a generic playback failure in the browser until the typed reason has a wire error. Resampler quality is measured with tones only; passband ripple is not characterised and there is no comparison with a reference resampler. The limiter has instant attack and no lookahead, so a sustained overload can add distortion; it is a clip guard, not a mastering limiter. Plain WAV files with four, five, seven or eight channels and no channel mask get the decoder's bit-order layout rather than the default speaker order, because the demuxer assigns it. Linux monitor evidence does not establish physical output, macOS, or browser-vendor behavior.

## Discover: MusicBrainz genres for imported music

Problem: on the live server Discover "By genre" was empty, because genres came only from local `GENRE` file tags and almost the whole library comes from Spotify imports without files.

Current behavior (runs on the local development server; migration 0069): the automatic matching walk gained a last pass that reads the official MusicBrainz `genres` (not free-form tags) of the artists the account chose (including automatic ISRC, artist page and name matches) and of the release groups and recordings named by retained file tag identities, caches them by MusicBrainz identifier for 30 days in `musicbrainz_genre_lookups` and `musicbrainz_genres` (provenance `musicbrainz`), and `Catalog::genres` and `genre` read them together with the file-tag rows. File tags win for a recording that has any; personal edits and artist choices are never touched. It uses the same consent (`automatic_artist_lookup`), the one request per second limiter, the separate background admission slots, bounded batches of eight lookups with a stored cursor (`genres:...` inside the provider phase), shutdown cancellation and the existing backoff for outages. A server start queues one walk for an account whose lookups are missing or older than 30 days. Only MusicBrainz identifiers leave the host; logs carry counts only. Details: [artist matching](artist-matching.md#musicbrainz-genres), [catalog browsing](catalog-browsing.md#genres-and-artist-radio), [adapter](builtin-musicbrainz.md#genre-lookups).

Tested evidence (Docker, assertion-level RED logs first for the client, core and HTTP slices, kept in the session scratchpad as `red-mb-genres-client.log`, `red-mb-genres-core.log` and `red-mb-genres-http.log`): five client protocol cases against the owned loopback fake (request targets, tags ignored, 404, 503, invalid answers, log redaction); nine core cases through the public capabilities with real temporary SQLite (artist genres in tiles and pages, file tag precedence, release group and recording identities from a FLAC file, outage then recovery, consent off sends nothing, special-purpose artists skipped, 30-day refresh and a finished account queued again, bounded batches with a resumable cursor and shutdown, logs without identifiers or names), one matching case for an imported library, one HTTP case through the real router, a work-budget case (40 against 300 artist-tagged tracks: 15,500 and 7,200 VM steps), account erasure (cache rows kept only for identities a remaining account names; the erasure plan completeness test classifies both tables) and migration 0069 in the schema, upgrade and maintenance fixtures. The cases written after the code (the imported-library matching case, the work-budget case and the HTTP case) were not run failing first; the HTTP case was shown failing by temporarily removing the genre phase.

Gates: formatting and all-target Clippy clean; the Rust batch passes 1,584 cases across 250 results with 5 ignored and no failures (a first batch failed the erasure completeness test and one maintenance snapshot bound, both fixed); the isolated browser run passes 50 specs. No web or wire type changed, so the contract and frontend gates were not re-run.

Limits: no request has reached the live MusicBrainz service, so coverage of real artists, the number of requests and the time to the first tiles are unknown; at one request per second a library with many distinct chosen artists takes that many seconds, and files with recording identifiers but no genre tag add one lookup per recording; the UI does not mark which genres came from MusicBrainz; artists chosen through plugins have no MusicBrainz identity and get no genres; imported tracks are not playable in the owned fakes, so the imported-library case checks the cache and the file-based cases check the tiles. Not a public release.
