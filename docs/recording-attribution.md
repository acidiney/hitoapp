# Retained provider credits

The development SDK can attach optional recording attribution to structured provider metadata. Core retains it on the existing immutable metadata observation and projects it through recording metadata history. Attribution describes the observed provider recording. It does not establish the source currently playing, a licence, permission to download, or a canonical recording match.

## Contract and ownership

`RecordingAttribution` contains ordered `creators`, a `provider_label` and a `content_url`. It accepts one to sixteen creators, each at most 2,048 UTF-8 bytes, and a provider label of at most 256 bytes. Text must be nonblank and contain no control characters. Creator order and repeated names are preserved.

The backlink is at most 2,048 bytes and must already be a canonical HTTPS URL. User information, queries, fragments, control characters, whitespace and backslashes are rejected. This first contract intentionally accepts no query parameters. It validates syntax; it does not resolve DNS or verify public accessibility, page ownership, licence terms or whether a path contains sensitive information. Providers must supply their public canonical content page.

The complete response still has its existing transport budget. Individual field maxima do not guarantee that all maximum-size fields fit one response. Nested attribution rejects unknown fields, missing required fields and incorrect types. Absence or null means no attribution; serialization omits absence, preserving legacy recording, search, playlist and metadata response bytes and existing manifest inputs.

The SDK owns this wire contract. Core owns provider validation, transactions, immutable observation identity and account access. The existing full-recording serialization and digest include supplied attribution. Identical details reuse the prior observation. Adding credits creates a new observation even if the provider revision stays unchanged, leaving older observations intact. Personal metadata overrides remain independent.

History reads borrow the retained provider JSON, enforce a 256 KiB input limit, deserialize only attribution and ignore unrelated provider fields. Retained attribution is validated again, with static errors that do not echo its contents. No migration, historical rewrite, additional SQL query, upstream lookup, audio request or download is introduced. Existing workflow logs retain their safe outcomes and correlations.

## Shared recording pages

The recording detail page now shows credits from its selected provider metadata observation. Metadata history shows each observation's retained credits separately. A shared component preserves creator order and repeated names, escapes text and renders a canonical HTTPS provider backlink with `noopener noreferrer` and no referrer. An invalid or noncanonical backlink leaves the provider label as plain text. Absent attribution creates no empty section. The shared wrapping rule also covers maximum-length unbroken names and labels.

The component uses the generated contract and introduces no requests, effects, playback subscriptions or provider-specific rendering. Personal title and artist edits remain independent. These credits describe metadata provenance; they do not identify the source currently playing or grant permission to download.

The first page regression failed on the missing credits section. Twenty-eight new cases now verify selected and historical credits, absent/null values, escaped markup, unsafe backlink rejection, late history responses and private edit isolation. They retain bounded log-privacy and request checks. All 391 cases in the feature snapshot and all 415 cases after integration pass, alongside both TypeScript configurations and the production build. Independent security and performance reviews pass. Correctness review found a wrapping gap for selected credits; the minimal shared rule and focused second review resolve it. Packaged checks follow below. Normal deployment and Jamendo account availability remain unfinished.

## Packaged browser verification

An isolated image built with the web assets from `733b57b` and the server executable from `f4afcf3` passes the complete recording-credit workflow in Chromium and WebKit. The old web package first fails on its missing credits section. The new package connects an owned HTTP provider through Settings, searches, saves a recording twice, checks its selected credits and two immutable history observations, pins an unavailable source and reloads. Creator order, duplicate names, escaped markup, protected backlinks and wrapping of maximum-length unbroken text pass in both engines.

The workflow makes exactly eight provider requests and no audio, preparation, persistent download, community or foreign browser request. Existing local recording edits, duplicate playlist entries, likes, progress, events and original WAV bytes remain unchanged. Browser debug output passes bounded private-canary checks. These checks do not establish general backend-log privacy, live-provider compatibility or playback performance.

Fifteen Chromium controls qualify the evidence collector, including a held response-body deadline, exact setup cancellation accounting, singular preparation polling, redirected requests and unload traffic. The raw cancellation count stays visible. Only the witnessed Chromium setup cancellation signatures can be accounted separately, before the verified account boundary; later, unknown and dropped failures remain terminal. Six applicable controls and the complete workflow pass in WebKit. Nine held-401 controls are explicitly Chromium-only because the Linux WebKit fixture does not expose those response headers while their bodies remain open. This is a fixture coverage limit, not a passing WebKit result for those nine cases.

Independent security, correctness and performance reviews pass after correcting the collector's singular-route matcher, redirect/unload accounting and bounded cleanup. Both TypeScript configurations pass. The disposable server is stopped; the normal server and listener accounts were untouched. This package predates the later Jamendo producer and initial plugin-consent changes, which require their own combined acceptance.
